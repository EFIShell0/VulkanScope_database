# VulkanScope Database 1.4.12 audit

## Scope
This release raises the new-report producer floor from VulkanScope 3.0.2 to 3.0.12 and repairs stale static preload snapshots without coupling report admission to a Pages deployment.

## Snapshot publication design
- D1 is authoritative. A valid new report is committed first.
- The Worker schedules a GitHub Actions workflow dispatch with `ctx.waitUntil()` only when the insert actually created a new row.
- Dispatch uses the repository-scoped `SNAPSHOT_GITHUB_TOKEN` Worker secret plus non-secret owner/repository/workflow/ref vars.
- The snapshot workflow runs separately from release publication, rebuilds the static index and preload from the live API, waits for the triggering report ID to appear, audits the staged Pages tree, deploys it, then verifies the published manifest contains the triggering report.
- Snapshot workflow runs are isolated from release workflow runs so report bursts can coalesce to the latest pending refresh. The actual Pages deployment jobs additionally share one queued concurrency group so release and snapshot artifacts cannot race each other onto the site.
- `/v1/sync` remains the immediate live-data path while snapshot publication catches up asynchronously.

## Security and failure boundaries
The GitHub credential is never embedded in frontend assets, configuration, report payloads, D1 data or API responses. Dispatch retries only transient network/429/5xx failures and is bounded inside the Worker background lifetime. Snapshot failure is logged and observable but does not roll back or reject an already accepted report.

## Compatibility
VulkanScope 3.0.12 / versionCode 3012 is the new accepted floor. Schema 2, technicalReport 3, Vulkan 1.4.364, normalizer 16, report IDs, D1 migrations and historical reads remain unchanged.

- The release deploy job and report-triggered snapshot deploy job share one queued Pages-deployment concurrency group, preventing a slower stale deployment from overwriting a fresher snapshot.
