# VulkanScope Database 0.39.7 Image Format Properties2 query-outcome separation / VulkanScope 0.41.9 audit

## Trigger
VulkanScope 0.41.8 preserved exact negative Image Format Properties2 tuple evidence inside normal `detailedProperties`. A real report therefore inflated the Properties & Limits evidence total by hundreds of unsupported tuples.

## Correction
VulkanScope 0.41.9 moves only non-success Image Format Properties2 tuple outcomes to `technicalReport.devices[].imageFormatQueryResults`. Database 0.39.7 normalizes and compares that dataset separately, while normal Properties/Limit aggregation continues to use actual detailed properties and query diagnostics only.

## Validation
For 0.41.9+ submissions the Worker requires a bounded query-result array. Tuple names are canonical and unique; `unsupported` requires numeric VkResult -11 (`VK_ERROR_FORMAT_NOT_SUPPORTED`), while `unavailable` requires another non-zero result. Negative tuple strings are rejected from 0.41.9 detailedProperties. Historical 0.41.8 tuple strings remain accepted only under the older producer contract.

## Compare and usability
The Compare map overlays separate non-success query outcomes onto the same `Image Format Properties2 / <tuple>` identity used by historical successful rows. Report detail Formats shows the outcome dataset in a dedicated table and states that it is excluded from Properties & Limits totals.

## Compatibility
Database schema 2, technicalReport 3, normalizer 15, D1 schema, report IDs/hashes and the 0.32.4+ producer floor remain unchanged.


## Final verification
Source audit, JavaScript syntax, hash-route contract, Compare contract, Worker contract, audit-hygiene regression, canonical repository-state check and allow-listed Pages artifact audit all pass. The tests explicitly prove that separated non-success tuples survive normalization and Compare while remaining absent from `detailedProperties`, and that malformed/duplicate/misclassified 0.41.9 tuple outcomes are rejected.
