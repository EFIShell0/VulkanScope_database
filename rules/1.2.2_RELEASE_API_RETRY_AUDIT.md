# VulkanScope Database 1.2.2 release API retry audit

- Predecessor 1.2.1 remains immutable; this release does not retarget `v1.2.1`.
- The release job retains job-scoped `contents: write`; all other jobs keep least privilege.
- GitHub Release discovery, creation and asset upload are state-aware and retry only transient GitHub API conditions (`HTTP 429`, `HTTP 5xx`, rate-limit/temporary-unavailable responses).
- Retry count is bounded to five attempts with increasing delay; non-transient failures fail immediately.
- Before any mutation, an existing tag/release must resolve to the validated `GITHUB_SHA`; a conflicting tag fails closed and requires a version bump.
- If GitHub created the release server-side but returned a transient 5xx to the client, the next attempt re-discovers that release and safely uploads assets with `--clobber` rather than trying to retarget the tag.
- D1 schema/migrations, report payload bytes/hashes, normalizer, Vulkan evidence semantics and the VulkanScope 1.2.5 submission floor are unchanged.
