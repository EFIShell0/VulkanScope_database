# VulkanScope Database 1.0.7 Windows checkout / npm subprocess audit

## Trigger evidence
The 1.0.6 rollout exposed two Windows-only failures that Linux/source-only tests did not reproduce:

1. `windows-tooling` failed the Encyclopedia regeneration byte comparison even though the generator emitted explicit UTF-8/LF bytes. The remaining platform variable was checkout line-ending conversion of the checked-in expected fixture.
2. Local production predeploy passed account verification but `security-audit.mjs` failed before npm could start with `spawnSync npm.cmd EINVAL`. The failure was command-launch mechanics, not an npm advisory result; the immediately preceding `npm install` reported zero vulnerabilities.

## 1.0.7 correction
- Root `.gitattributes` makes repository text LF-only and excludes binary artwork from text conversion.
- Encyclopedia verification continues to require byte identity and now emits a specific checkout-line-ending diagnostic instead of masking CRLF.
- Security audit invokes npm's JavaScript CLI via the running Node executable; direct `npm.cmd` spawning is forbidden.
- Existing package locks are reused; absent locks are bootstrapped only as ignored deployment-workspace state, then exact Wrangler/sharp resolutions and integrity metadata are checked before the high-severity audit.
- Windows CI installs the Worker dependency graph and runs the actual security-audit npm script. setup-node v7 / Node 24 is explicit on both Windows tooling and Linux build jobs. A network-independent runner state-machine also executes the real helper against a fake npm CLI to prove exact argv, existing-lock reuse, missing-lock bootstrap, and high-severity audit invocation.

## Preserved contracts
VulkanScope 1.0.15 / 1015, Vulkan 1.4.362, submission schema 2, technicalReport 3, normalizer 16, D1 schema/migrations, report hashes, payload storage and preload/live-delta behavior remain unchanged. No D1 migration or stored-report rewrite is introduced.

## Evidence classes
Static/source, mutation, regression, Worker/D1 and clean-extract checks can be executed in the release packaging environment. A real `windows-latest` run and network-backed npm audit are separate runtime evidence and must not be reported as PASS until actually executed by the pushed workflow/operator environment.
