# VulkanScope Database 1.0.20 release-state handshake audit

## Failure addressed
Database 1.0.18 interpreted the Worker's `databaseVersion` as proof that a newer Pages frontend was safe to refresh into. If the Worker was deployed first, or if Pages deployment failed, the old frontend repeatedly saw the newer Worker version and could re-offer Refresh while the old Pages build was still the only build available. Database 1.0.19 moved the new frontend to a Pages marker but could not stop already-published 1.0.18 code from reading the Worker field.

The 1.0.19 workflow also moved Pages deployment to a tag-ref job. GitHub's Pages documentation notes that Pages deployment must satisfy the configured source/environment protection rules, and the documented custom workflow uses `upload-pages-artifact@v4` plus `deploy-pages@v4`. Release 1.0.20 removes the tag-ref dependency and returns Pages publication to the validated `main` ref while still making GitHub Release completion a hard predecessor of deployment.

## 1.0.20 design
- `/v1/health` and `/v1/reports` no longer expose the legacy `databaseVersion` key. This immediately makes cached 1.0.18 frontends stop treating Worker rollout as frontend readiness. Accurate Worker/Database release identity is exposed through `databaseReleaseVersion` and `workerReleaseVersion` and explicitly labels the frontend signal as `same-origin-pages-marker`.
- Source `data/release.json` is schema 2 and `releaseReady:false`. It names the exact frontend asset and cache key.
- Only `tools/mark_release_ready.py` flips the staged Pages copy to ready, and the workflow calls it only after GitHub Release success.
- The deploy job rebuilds/stages/uploads the artifact itself after Release success. It does not reuse the build job's Pages artifact.
- Browser update checks require marker + index + application-asset agreement under no-store fetches before displaying Refresh.
- Session-scoped retry suppression prevents the same target version from immediately re-prompting if a cache-busted navigation still returns the old frontend.
- Main-branch production deployment uses `configure-pages@v5`, `upload-pages-artifact@v4`, `deploy-pages@v4`.

## Immutable boundaries
No D1 migration or report rewrite is introduced. Vulkan 1.4.362/header 362, schema 2, technicalReport 3, normalizer 16, producer minimum VulkanScope 1.0.19, report hashing, security limits and all 1.0.19 data/evidence semantics remain unchanged.
