# VulkanScope Database 0.39.13 — Windows UTF-8 quality-gate regression audit

## Confirmed predecessor failure
On Windows Python 3.13, `tools/verify_vulkanscope_04132.py` used `Path.read_text()` without an explicit encoding. The host selected CP1252 and failed on byte `0x90` in `assets/app.v03912.js` before any Vulkan compatibility assertion ran.

## Fix
All Python `Path.read_text` / `Path.write_text` calls under `tools/` are now explicit about UTF-8 (or preserve an already explicit intentional policy). The D1 migration-chain loader also reads SQL as UTF-8. The current frontend is cache-busted as `app.v03913.js`; its technical behavior is unchanged apart from the displayed Database release identity.

## Regression gate
`tools/test_utf8_text_io.py` AST-checks every Python tool for implicit Path text I/O, verifies the real frontend byte stream still fails CP1252 while decoding as UTF-8, and executes the VulkanScope 0.41.32 compatibility verifier. The test runs both directly in the Pages workflow and from the aggregate quality gate.

## Non-goals
No Worker request/response validation, D1 schema, report hash, report payload, normalizer, VulkanScope 0.41.32 contract, Vulkan 1.4.361 registry lock, transport ceiling or privacy/security policy is changed by this release.

## Installed-workspace regression behavior
The predecessor regression verifier recursively inspected every local file. In the user's real sequence (`npm ci` before `python tools/quality_gate.py`), dependency installation output and an existing repository `worker/package-lock.json` could therefore be misclassified as release-source regressions. 0.39.13 explicitly ignores only contract-declared generated/local paths. When `worker/package-lock.json` is present, a separate verifier requires Wrangler 4.125.0 to be both root-pinned and resolved with an integrity hash.
