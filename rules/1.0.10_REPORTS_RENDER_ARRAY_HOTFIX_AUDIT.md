- Submission schema 2 / technicalReport 3 / normalizer 16
- D1 migration: none

## Reproduced failure
Database 1.0.9 constructed the Reports body as `rs.map(...).join('')` and then passed that string into the shared `table(heads, rows)` helper. The helper intentionally serializes a row array with `rows.join('')`, so Reports raised `rows.join is not a function` before the table could render. This was a frontend type/ownership regression, not a Worker/D1 availability failure.

## Repair
- `renderReports()` keeps the result of `rs.map(...)` as an Array and passes that Array directly to `table()`.
- `table()` remains the single owner of row serialization. It is not weakened to silently accept the wrong type.
- The exact 1.0.9 Date/Time/Time-zone stack, full 64-character Report ID copy action, atomic live reconciliation, low-percentage coverage treatment and VulkanScope 1.0.19 submission floor are retained unchanged.
- Browser-visible JavaScript advances to `assets/app.v1010.js` with cache key 1010 so GitHub Pages/browser caches cannot retain the broken 1.0.9 script.

## Regression boundary
No D1 migration, stored report rewrite, report-ID/hash rewrite, schema change, normalizer change, Vulkan registry corpus change, payload-storage change, transport/CORS weakening or evidence-state semantic broadening is introduced.
