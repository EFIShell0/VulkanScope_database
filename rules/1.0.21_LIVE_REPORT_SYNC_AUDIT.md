# VulkanScope Database 1.0.21 live-report synchronization audit

## Failure addressed
A report accepted by the Worker could remain absent from an already-open Database page until manual reload. The previous frontend performed a complete `/v1/reports` reconciliation every ten seconds and silently swallowed refresh failures. The design was both heavier than necessary and did not provide a narrow, cache-resistant freshness signal.

## 1.0.21 design
- Add a GET-only `/v1/sync` Worker endpoint backed by one D1 window query. It reports the current row count and newest `(submitted_at, id)` identity as a deterministic token.
- Poll that lightweight token every three seconds while the tab is visible/online. All freshness requests are no-store and nonce-busted.
- Re-fetch the full cursor-safe index only when the token changes. Fetch only report payloads absent from the current committed Map.
- Commit the new Map/index only after every expected report payload is available; then re-render metrics and the active view immediately.
- Force a complete reconciliation on visibility return, focus, pageshow and online recovery so background throttling cannot leave the page stale.
- Keep the previous committed token/Map on any failure so the next tick retries instead of falsely declaring the stale state current.

## Immutable boundaries
No D1 migration, stored-report rewrite, report-ID/hash change, producer-floor change or Vulkan evidence semantic change is introduced. Exact duplicate canonical reports remain deduplicated by their stable report ID. The 1.0.20 Pages release-ready handshake remains the only frontend update signal.
