# VulkanScope Database 1.0.1 full security / evidence-semantics audit

## Immutable predecessor
- VulkanScope Database 1.0.0
- ZIP SHA-256: `2199e7cec2d86caa9c652f194166ccaa1c9b7391a4e5cd0895dbfd38e5129e7a`
- Predecessor package census: 216 files

## Demonstrated defect
The 1.0.0 report-detail Surface renderer derived `Available` and `Presentation supported` badge states directly from Boolean values. A `false` value could therefore be shown as a negative capability result even when the authoritative Surface query state was `incomplete`, `unavailable`, `not_applicable` or `unknown`. The Worker report-text normalizer also assigned those two item statuses while parsing the Boolean line, making the result depend on whether the `Query status=` line had already been seen.

This violated VulkanScope Database's evidence rule that missing, incomplete or unavailable evidence must not be converted into `Unsupported`.

## 1.0.1 correction
- The Worker retains explicit Surface query states: `available`, `incomplete`, `unavailable`, `not_applicable`, and `unknown`.
- `Available=false` is not promoted to a definitive negative state when the query itself is incomplete/unknown/not-applicable.
- `Presentation supported=false` becomes `unsupported` only when the authoritative Surface query completed as `available`; otherwise it follows the non-terminal evidence state.
- Surface report-text parsing stores raw Boolean values first and synchronizes normalized item states after the full Surface section has been parsed, so line order cannot change semantics.
- The Pages frontend uses the same query-aware Surface helpers for the visible detail cards instead of direct Boolean classification.
- Current producer metadata advances to VulkanScope 1.0.1 / versionCode 1001 / Vulkan 1.4.362 while retaining historical VulkanScope 1.0.0/1000 and 0.80.x compatibility.
