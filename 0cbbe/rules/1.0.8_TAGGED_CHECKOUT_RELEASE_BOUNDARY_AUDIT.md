# VulkanScope Database 1.0.8 tagged-checkout / strict-package boundary audit

## Observed failure
The GitHub tag `release` job ran `tools/verify_regression_contract.py --strict-tree` directly against the tagged long-lived repository checkout. That checkout legitimately retained historical tracked frontend assets such as older `assets/site.v*.css` files and `assets/app.js` that were never members of the immutable 1.0.7 release ZIP. Strict-package mode therefore rejected repository history before the deterministic packager had a chance to construct its allow-listed artifact.

## Correction
- Tagged/raw source checkouts are validated with source-overlay mode.
- The deterministic packager derives the exact release member set from the immutable predecessor manifest plus explicit successor changes.
- Local `worker/package-lock.json` and unrelated repository-history files are not package members.
- The ZIP is clean-extracted and its exact path set and bytes are compared with the selected source.
- `--strict-tree` and source audit run from inside that clean extract.
- GitHub Release publication occurs only after the package itself passes those strict checks.

## Regression evidence
`tools/test_1_0_8_release_checkout_packaging.py` injects representative historical `assets/site.v0380.css`, `assets/site.v0357.css`, and `assets/app.js` files into a copied source checkout. Source-overlay verification must accept them, release packaging must exclude them, the clean package must pass strict-tree, and a deliberately injected release-tree extra must fail strict-tree.

## Unchanged contracts
VulkanScope 1.0.15/1015, Vulkan 1.4.362, schema 2, technicalReport 3, normalizer 16, D1 migrations/storage, report IDs/hashes, payload/privacy/CORS semantics, Worker producer validation, and preload/live-delta behavior are unchanged. No D1 migration or stored-report rewrite is introduced.
