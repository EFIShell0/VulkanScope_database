## Confirmed rejection defect
Database 0.39.26 selected registry versions correctly but compared `vulkan.registryBaseline` and `technicalReport.registryCoverage.baseline` against bare `1.4.362` or `1.4.361`. The application producer stores the locked catalog baseline itself in these fields. VulkanScope 0.80.12 therefore emits `Vulkan 1.4.362`, and VulkanScope 0.80.9 emits `Vulkan 1.4.361`.

The 0.39.26 Worker contract repeated the same bare-version spelling in its fixtures, so its HTTP 201 test did not model the actual producer string and could not expose the production rejection.

## Correction
0.39.27 keeps the registry version selector but constructs the required baseline as `Vulkan ${registryVersion}`. Header provenance is derived from that exact baseline. No submitted value is rewritten or normalized at ingest.

Worker fixtures now use the actual producer strings. Negative fixtures explicitly prove that bare `1.4.362` and `1.4.361` are rejected rather than accepted as aliases.
