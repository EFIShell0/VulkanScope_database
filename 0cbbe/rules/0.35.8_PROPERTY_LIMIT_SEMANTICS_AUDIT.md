# VulkanScope Database 0.35.8 Properties / Limits semantics audit

## Trigger
A VulkanScope 0.33.10 Turnip report displayed 1469 property query results, 1330 unique property names and 106 limits, while VulkanScope Database 0.35.7 displayed 1482 Properties.

## Root cause
The Database used a broad normalized `capabilities` collection for the Properties view. The TXT normalizer intentionally contains compatibility rows for DEVICE, SURFACE and other technical sections, and `propertyCandidate()` excluded only a subset of non-property sections. As a result, report metadata could inflate the Properties count. The Limits view also used a section-name heuristic matching `Limits|Sparse Properties`, allowing true detailed-property sections to overlap with Limits.

## Fix
- Schema-v3 `devices[].detailedProperties` is copied to a dedicated normalized `detailedProperties` array and is authoritative for Properties.
- Schema-v3 `devices[].limits` is copied to a dedicated normalized `limits` array and is authoritative for Limits.
- TXT fallback builds the same two arrays from bracketed non-feature query rows and the literal LIMITS section.
- Aggregate and detail views consume the dedicated arrays instead of broad `capabilities` heuristics.
- The broad capability collection remains for legacy Compare/raw compatibility only.

## Expected producer parity
For a schema-v3 report, the Database report-detail Properties count equals `technicalReport.devices[selected].detailedProperties.length`; the Limits count equals `.limits.length`. Therefore a producer display of 1469 property query results and 106 limits is represented as 1469 Properties and 106 Limits, not as a combined or metadata-inflated count.

## Migration
None. Stored payloads already contain the authoritative structured arrays and are reinterpreted on read.
