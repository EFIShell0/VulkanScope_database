# VulkanScope Database 0.36.5 — VulkanScope 0.35.1 Full Database Audit

Date: 2026-08-24

## Scope

This audit validates VulkanScope Database against VulkanScope 0.35.1 / versionCode 352, submission schema 2 / technicalReport schema 3, the published Vulkan 1.4.360 metadata, Worker validation, frontend normalization, complete-report destinations, privacy/security bounds and existing D1 compatibility.

## Producer contract hardening

Database 0.36.3 advertised a VulkanScope 0.32.4+ compatible producer contract but did not fully enforce that producer floor/canonical version shape in the Worker. It also did not bind the current VulkanScope 0.35.1 producer to versionCode 352. Database 0.36.5 makes those declared invariants executable validation rules.

Producer versions must be canonical compatible 0.x releases at or above 0.32.4. VulkanScope 0.35.1 must use versionCode 352. This does not invalidate earlier compatible schema-2 / technicalReport-3 producers.

## Duplicate platform evidence

The producer submits application ABI and supported-device ABI values both at the top level and in technicalReport. These are duplicate evidence of the same facts and must agree exactly; disagreement is rejected instead of being silently normalized. Android security patch must use canonical YYYY-MM-DD syntax.

## Reporting parity

The Database continues to expose device identity and API/driver data, instance/layer/device extensions, features, detailed properties, limits, formats including 64-bit VkFormatProperties3 feature masks, memory heaps/types, queues, Surface/WSI evidence, Display/HDR, profiles, registry provenance, Compare and Raw/canonical report evidence. Structured detailedProperties remains generic so validated future fields are not silently dropped by an extension-specific frontend whitelist.

Unknown, Unsupported, Unavailable and Not applicable remain distinct. Missing information is not promoted into unsupported or supported state based on GPU/vendor/device identity.

## Security and reliability

- Request body remains bounded to 2 MiB.
- Stored and incoming JSON are validated and canonicalized before hashing/storage.
- Sensitive identifier classes remain recursively rejected.
- Request IP is not stored as report data.
- D1 access remains parameterized.
- Browser Origin restrictions, CSP and API hardening remain intact.
- Frontend API reads retain timeout/body bounds, repeated-cursor protection and bounded detail concurrency.
- Submission remains explicit and user initiated.

## Storage

No D1 migration or stored-report rewrite is required. Existing reports and SHA-256 identities remain unchanged.
