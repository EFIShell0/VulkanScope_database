# VulkanScope Database 0.38.0 Statistics / Hash Routing / VulkanScope 0.41.4 Full Audit

## Scope

This audit covers the complete 0.37.1 → 0.38.0 Database source tree against `rules/PROJECT_RULES.md`, VulkanScope 0.41.4 producer semantics, current Vulkan 1.4.360 metadata, Cloudflare Worker security constraints, frontend usability/design consistency, report completeness, routing, performance bounds and release packaging.

## Verified issues in 0.37.1

1. Static HTTP error pages referenced the removed `/assets/site.v0357.css`, so standalone 4xx/5xx pages could render without the intended Database design.
2. Public navigation/permalinks were query-string based and did not provide a stable URL for every main page or human-readable report section.
3. Statistics were table-only; there was no CapsViewer-style distribution visualization.
4. The Worker current-producer identity table ended at VulkanScope 0.41.3 / 413 and did not yet model VulkanScope 0.41.4 / 414 as the current producer.
5. VulkanScope 0.41.4 intentionally emits `null` numeric Vulkan Video queue-operation fields for unavailable/not-applicable/unknown query states; 0.37.1 did not fail-closed validate this new current-producer invariant.
6. Structured device-level query diagnostics (`deviceExtensionStatus`, `extendedQueryStatus`, `vulkan14Status` and reasons) existed in the producer report but were not surfaced as a dedicated report-detail diagnostic block.
7. The published JSON Schema did not list `technicalReport` as top-level required even though the Worker complete-report contract requires schema-2 / technicalReport-3 submissions.

## 0.38.0 corrections

### Routing

- All primary views emit canonical hash routes.
- Reports emit `#reports/<id>/<Section>` with a lowercase 64-hex loaded id and allow-listed section.
- Compare emits exactly two loaded report ids.
- Back/forward and hash changes are handled.
- Valid legacy query routes are migration inputs only.

### Statistics

- Added local SVG/CSS donut charts for exclusive loaded-report dimensions.
- Percentages are loaded-submission share only.
- Extension membership remains a frequency table because extensions overlap.
- `Other` grouping bounds chart legibility without modifying source reports.

### Producer compatibility / report correctness

- `report.schema.json` now requires the existing technicalReport member so published schema validation matches the Worker complete-report contract. This is contract-description alignment, not a schema-version or D1 migration.

- Current producer baseline is VulkanScope 0.41.4 / 414.
- Schema 2 / technicalReport 3 remain unchanged.
- Queue/video query status preserves queried zero separately from unavailable/not-applicable/unknown.
- Non-available current-producer queue-video states require null numeric masks.
- Device extension enumeration, extended feature/property and Vulkan 1.4 runtime query status/reason evidence is preserved in report Registry detail and Compare, with current-producer status values validated fail-closed.
- No capability is inferred from GPU name, vendor, Android version or missing evidence.

### Security and privacy

- No third-party chart/runtime dependency was added.
- Worker request bodies remain bounded and streamed.
- CORS, CSP, privacy-field rejection and D1 parameter binding are preserved.
- URL route ids and detail sections are validated before state changes.
- Local error-page asset references are verified by release audit.

### Usability / design consistency

- Statistics use the Database visual hierarchy and existing first-party design tokens.
- Hash routes make pages bookmarkable and improve browser navigation.
- Charts include text legends/counts/percentages and an accessible image role/label.
- Existing state colors retain their semantic meaning; chart colors are decorative distribution colors rather than support-state colors.

### Optimization

- Inline SVG/CSS charts add no runtime network request.
- Report-fetch concurrency remains bounded.
- Report table pagination remains at or below 50 rows per page.
- Chart slices are visually bounded while counts remain exact for the loaded filtered set.

## Specification / platform baseline

- Published Vulkan specification metadata: Vulkan 1.4.360 (2026-08-14).
- Worker compatibility date remains the project deployment-verified 2026-08-23 per project rules; it is not advanced without a real deployment validation.
- Wrangler remains pinned to 4.125.0.

## Storage compatibility

No D1 migration, report rewrite, hash rewrite or schema migration is required.

## Validation boundaries / operational notes

- This source audit and contract suite does not replace a real Cloudflare Pages/Workers deployment smoke test, browser matrix, or production D1 load test.
- The Worker compatibility date therefore remains the last deployment-verified project date rather than being advanced only to satisfy recency.
- The frontend intentionally preserves complete loaded-report semantics. Report fetches remain bounded by concurrency and per-response limits; no silent global report truncation was introduced merely to reduce memory usage. For very large future datasets, server-side aggregate/statistics endpoints or lazy report-detail loading would be the next optimization step, but that is not required for the current schema/storage release and would be a larger architecture change.
- Public report submission remains intentionally unauthenticated by project design. Payload size limits, strict schema validation, privacy-field rejection, CORS, deterministic hashing and D1 prepared bindings remain application-level controls; deployment-level Cloudflare rate limiting/WAF remains an operator control and is not simulated by this source audit.

## Release verification

The release verifier requires current version/asset metadata, current producer identity, normalizer 15, hash-route invariants, chart semantics, current local error-page assets, Worker security invariants, JSON/schema parsing, JavaScript syntax and Worker contract tests to pass.
